# Учётка и доступ к папкам

У каждого приложения своя учётка на NAS — как отдельный ключ у сантехника: он открывает только
нужную дверь. Приложение видит свои данные и те общие папки, к которым вы дали доступ, и больше ничего.
Права пользователей NAS при этом не меняются.

## Что вы видите
- **От чьего имени работает** — для каждого сервиса приложения:
  - **своя учётка (рекомендуется)** — программа в контейнере работает от учётки `app-<идентификатор>`;
  - **своя учётка через PUID/PGID** — для образов, которые сами переключаются на нужную учётку
    (например, образы linuxserver.io): контейнер стартует с полными правами, затем программа
    продолжает работу от учётки приложения;
  - **как root (без ограничений)** — для образов, которые иначе не работают. Права на папки для
    такого сервиса не действуют: защищает только монтирование «только чтение».
  Режим подбирается сам по compose; менять стоит, если приложение не запускается.
- **Доступ к общим папкам** — каждая папка, которую compose подключает к приложению:
  **только чтение** (по умолчанию) или **чтение и запись**.
- В карточке приложения — **Учётка и доступ к папкам**: имя учётки, номер (UID), выданные папки,
  кто и когда выдал.
- **Доступ как root** — значок у приложений, добавленных раньше, чем появились учётки приложений.

## Как это работает
1. При создании приложения появляется его учётка, данные приложения переходят к ней.
2. На выбранные папки ставятся права только для этой учётки (на все вложенные файлы и папки).
   В большой папке это занимает время — ход виден в задаче.
3. Новые файлы, которые приложение создаёт в папке с правом записи, принадлежат учётке приложения,
   а группа у них — общая группа пользователей NAS с правом записи. Поэтому пользователи NAS видят
   и могут менять их по сети, как обычно. В Windows владелец показывается как «Unix User\app-…».
4. Если снять доступ, права учётки убираются со всей папки. Файлы, которые приложение успело
   создать, остаются на месте.
5. Раз в 10 минут NAS сверяет права с выданными. Если они сбились (например, папку вернули из
   снимка), права восстанавливаются сами, а в журнал пишется событие.

## Что делать
- Приложение не запускается со своей учёткой — откройте **Изменить**, выберите
  **своя учётка через PUID/PGID** или, если не помогло, **как root**, и нажмите **Проверить**.
- Значок **Доступ как root** — откройте приложение и нажмите **Перевести на свою учётку**.
  Доступ к папкам предложен как было: подключённые без «только чтение» — с записью. При сбое
  перевода всё возвращается как было.

## Чего не делать
- Не давайте запись в папку, если приложению достаточно чтения: медиасерверу для показа фильмов
  запись не нужна, а взломанное приложение с записью может испортить файлы.

См. также: [Добавить приложение](help:apps.add), [Риски](help:apps.risks).

:::details Для администратора
Учётка приложения — `app-<id>` с номером (UID = GID) из диапазона 59000–59999, без входа в систему и
без домашнего каталога; номер удалённого приложения повторно не выдаётся. Права на папки — POSIX ACL
(проверить: `getfacl <папка>`); символьные ссылки при выдаче прав не обходятся. Владелец файлов
общих папок не меняется.
:::
